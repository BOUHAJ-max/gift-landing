تعلم فروع Git: branch وmerge وحل التعارضات

دليل عملي لفهم فروع Git وإنشاء branch ودمج التغييرات وحل التعارضات دون فقدان عملك.

دليل تقني عملي•إعداد: Mohamed Bouhaj•BOUHAJ TECH

محتويات المقال

1. ما هو الفرع؟2. إنشاء فرع والعمل عليه3. التنقل بين الفروع4. دمج التغييرات5. فهم التعارض وحله6. إرسال الفرع إلى GitHub7. سير عمل عملي بفروع قصيرة8. التراجع بأمان

تسمح فروع Git بتجربة ميزة أو إصلاح خطأ بمعزل عن النسخة الأساسية للمشروع. هذا المقال يشرح سير عمل بسيطاً للمشاريع الفردية والفرق الصغيرة.

1. ما هو الفرع؟

الفرع مؤشر إلى سلسلة من الالتزامات (commits). عند إنشاء فرع جديد يمكنك تعديل الملفات وتسجيل التغييرات دون تغيير الفرع الأساسي حتى تقرر الدمج.
git status
git branch

2. إنشاء فرع والعمل عليه

ابدأ من حالة نظيفة قدر الإمكان، ثم أنشئ فرعاً باسم واضح:
git switch -c feature/contact-page
# عدّل ملفات مشروعك
git status
git add .
git commit -m "Add contact page"

اجعل كل commit صغيراً وله رسالة تشرح التغيير. تجنب إدخال ملفات سرية أو مخرجات بناء غير لازمة.

3. التنقل بين الفروع

اعرض الفروع وانتقل إلى فرع موجود:
git branch
git switch main

إذا كانت لديك تعديلات غير محفوظة فقد يمنع Git التنقل لتجنب الكتابة فوقها. احفظها في commit أو استخدم stash بعد فهمه.

4. دمج التغييرات

بعد مراجعة التغييرات والاختبارات، انتقل إلى الفرع المستهدف ثم ادمج:
git switch main
git merge feature/contact-page

راجع الملفات المتغيرة واختبر المشروع بعد الدمج.

5. فهم التعارض وحله

يحدث التعارض عندما يعدّل فرعان الجزء نفسه من ملف بطريقة لا يستطيع Git جمعها تلقائياً. افتح الملف وابحث عن العلامات <<<<<<< و======= و>>>>>>>، واختر الصيغة الصحيحة يدوياً، ثم احذف العلامات واختبر النتيجة:
git status
# أصلح الملف يدوياً
git add path/to/file
git commit

لا تحذف أحد الجانبين عشوائياً؛ افهم التغييرين أولاً.

6. إرسال الفرع إلى GitHub

بعد إعداد remote للمستودع، أرسل الفرع للمراجعة:
git push -u origin feature/contact-page

استخدم Pull Request لشرح الهدف والاختبارات. لا تضع Personal Access Token داخل عنوان remote أو ملف المشروع.

تمرين: أنشئ فرعاً باسم feature/readme، عدّل README، أنشئ commit، ثم ادمجه في main محلياً.

7. سير عمل عملي بفروع قصيرة

استخدم فرعاً مستقلاً لكل ميزة أو إصلاح واضح، وابدأ دائماً من نسخة حديثة من الفرع الرئيسي:

git switch main
git pull --ff-only
git switch -c feature/search-filter
# عدّل الملفات ثم راجع التغييرات
git status
git diff
git add path/to/changed-file
git commit -m "Add search filter"
git push -u origin feature/search-filter

قبل فتح Pull Request، تأكد من أن التغيير محدود، وأن الاختبارات أو خطوات التحقق موثقة. لا تستخدم git add . بشكل آلي قبل فحص الملفات؛ فقد يضيف ملفات إعداد محلية أو أسراراً بالخطأ.

إذا كان الفرع الرئيسي قد تقدم، حدّث فرعك وفق سياسة المشروع. لا تعِد كتابة تاريخ فرع مشترك دون تنسيق مع الفريق.

8. التراجع عن الأخطاء دون فقد العمل

قبل أي أمر يغيّر التاريخ، افحص الحالة وسجّل نقطة رجوع عند الحاجة:

git status
git log --oneline -5
git diff
  • git restore file يعيد ملفاً من نسخة العمل إلى حالته المسجلة، وقد يحذف تعديلاتك غير المحفوظة على ذلك الملف.
  • git revert COMMIT ينشئ commit جديداً يعكس تغيير commit سابق، وغالباً يكون مناسباً للفروع المشتركة.
  • git stash push -m "temporary work" يحفظ تعديلات مؤقتاً لتعود إليها لاحقاً، لكن راجع محتواها قبل التنقل.

تجنب git reset --hard وفرض الدفع --force إذا لم تكن متأكداً من أثرهما؛ فقد تفقد عملاً أو تستبدل تاريخاً يعتمد عليه الآخرون.

مهمة: أنشئ commit تجريبياً، ثم استخدم revert لإلغاء أثره مع إبقاء سجل واضح يشرح ما حدث.
الخلاصة:

تعلم هذه المفاهيم بالتدرج وطبّق الأمثلة داخل بيئة تملكها. راجع التوثيق الرسمي للأدوات قبل استخدامها في بيئة إنتاجية.
